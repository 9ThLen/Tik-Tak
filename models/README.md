# Артефакти моделей

Тут живуть ваги моделей — а точніше, тут живе **облік** ваг: `manifest.json` з
закріпленими SHA-256, джерелами й ліцензіями. Самі файли в git не потрапляють
(`.gitignore` поруч), бо 79 МіБ ONNX в історії — це назавжди; репозиторій
фіксує, *яким байтам довіряємо*, а не байти.

Ліцензії й джерела перевірені в [`docs/ml-models.md`](../docs/ml-models.md).
Коротко: BeatNet — CC BY 4.0 (онлайн; поширення під App Store DRM потребує
окремого дозволу/юридичної перевірки), Beat This! — MIT включно з вагами
(офлайн-аналіз і псевдо-мітки).

## Чому такий обхідний шлях

Звичайне середовище розробки не має прямого доступу до всіх model hosts:
проксі ріже частину GitHub-релізів, huggingface і zenodo. Тому сума,
«пригадана» чи переписана з вебсторінки, була б вгадуванням у
шістнадцятковому записі. Замість цього — **довіра при першому отриманні**:
перший успішний `pin` у середовищі з доступом обчислює хеш і записує його в
маніфест; коміт цієї зміни і є актом поруки за артефакт. Кожен наступний
`verify` тримає файл за той хеш.

Офіційний Beat This! `small0` уже отримано через закріплений URL: 8 451 101
байт, SHA-256
`6074be2c4d490c5f6101fcc374a1ec72ae93456e23bb6019783b849f5dc7d47b`.
Сам checkpoint лишається поза git, а hash і provenance входять у
`manifest.json`.

Від чого це захищає — не від цільової атаки, а від буденного: повторне
завантаження, що тихо принесло інший файл; проксі, що віддав сторінку помилки
зі статусом 200; share-посилання, вміст якого з'їхав. Скрипт відмовляється
закріплювати HTML під виглядом моделі й розмір, що розходиться з задокументованим
на порядок.

```
python models/fetch.py list
python models/fetch.py pin beatnet_model_1 /шлях/до/model_1_weights.pt
python models/fetch.py pin beat_this_small https://cloud.cp.jku.at/public.php/dav/files/7ik4RrBKTS273gp/small0.ckpt
python models/fetch.py verify                              # тримає за хеш
```

Тільки stdlib — скрипт запускається на будь-якій машині з мережею без
установлення чогось.

Якщо артефакт уже закріплений у маніфесті, звичайний `pin` не створює нової
довіри: він приймає лише байти з уже довіреним SHA-256. Так у свіжому clone
відновлюється відсутній, проігнорований git файл без переписування маніфесту.
Інший SHA-256 буде відхилено зі збереженням наявного файла та pin. `--force`
потрібен лише для свідомої заміни кореня довіри, чий manifest diff треба
перевірити й пояснити.

### Блокування, атомарність і provenance

Шлях або URL, переданий аргументом `pin`, — лише спосіб доставити байти на цю
машину. Він **не записується** в маніфест: локальний шлях на кшталт
`C:\Users\name\Downloads\...` не є відтворюваним джерелом і може розкрити ім'я
користувача. Перед закріпленням перевірте поля `source` відповідного артефакту:
репозиторій/URL, шлях усередині репозиторію і, коли upstream його надає,
незмінний `revision` (commit або tag). `pin` копіює весь вкладений `source` у
`pinned.provenance.source`, а SHA-256 фіксує точні байти. Для сирих upstream-ваг
цей фінальний `pinned.sha256` водночас є `source_weights_sha256`, тому дублювати
його не треба.

Похідний ONNX додатково має блок `conversion`, який також незмінно копіюється в
`pinned.provenance`: SHA-256 вихідних ваг, репозиторій і revision/version
експортера, ONNX opset, preprocessing та контракт входів/виходів. `null`
допустимий, доки артефакт є лише кандидатом для дослідження, але перед включенням
у production-збірку всі ці поля мають бути заповнені перевіреними значеннями.
Локальний delivery-path до цього snapshot ніколи не входить.

Копіювання або завантаження відбувається в тимчасовий файл поруч із цільовим.
HTML-пастка, розмір і SHA-256 перевіряються **до** атомарного `replace`.
Невдалий `pin --force` тому не чіпає попередній перевірений файл чи його запис
у маніфесті. `pin`, `verify` і `list` серіалізовані між процесами advisory-lock
поруч із маніфестом, а сам маніфест також записується через тимчасовий файл.
Тому паралельні pin не гублять зміни одне одного; блокування автоматично
звільняє операційна система після завершення або аварії процесу.

Атомарним є `replace` **кожного окремого файла**, а не пара «артефакт +
маніфест» як єдина транзакція файлової системи. Звичайна помилка запису
маніфесту відкочує встановлення артефакту. Раптове вимкнення процесу точно між
двома replace може лишити новий артефакт зі старим pin або артефакт без pin;
наступний `verify` відхиляє обидва стани (mismatch або `exists but is not
pinned`), а не видає їх за перевірені. Файл `.backup`, що міг лишитися після
такої аварії, зберігає попередні байти для ручного відновлення.

## Як оцінити модель до того, як портувати її

Це найважливіше, що вміє цей етап, і працює воно вже зараз, без ONNX Runtime
у C++. Шов описано в `core/src/analysis/downbeat.hpp`: скоринг «наскільки ця
доля схожа на межу такту» відділений від резолвера «який розмір і фаза з цього
випливають». `dump_analysis --salience <file>` подає в **той самий** резолвер,
що працює в застосунку, зовнішню пер-бітову виразність:

```python
from eval.analysis import Analyser

analyser = Analyser()
grid = analyser.analyse_file("song.mp3")            # прохід 1: сітка бітів
activation = model_activation_at(grid.beats)        # модель, семпльована в бітах
result = analyser.analyse_file("song.mp3", salience=activation)
```

Або через `research/eval/backends.py`, який тримає скоринг і його калібровку
разом і підключений до benchmark:

```
.venv/bin/python -m eval.downbeat_benchmark --backend beat_this --dataset ~/clips
```

Бекенд без чекпойнта **відмовляється**, а не відкочується на підказки: прогін,
який тихо оцінив би вбудований скорер і надрукував угорі назву моделі, виглядав
би точнісінько як результат.

`result` має ті самі поля, але margin'и лишаються в одиницях backend, який
подав salience. Резолвер прибирає лише сталий зсув і не перетворює майже
плоский вихід на повномасштабний сигнал. Тому `min_salience_range`,
`min_phase_margin` і `min_meter_margin` калібруються для кожного backend як
один набір — і саме тому вони їздять одним об'єктом `Calibration`, а
`dump_analysis` приймає всі три прапорці разом або жодного. Половина
калібровки — це `downbeat_confident`, порахований числами чужого скорера.
**Моделі все одно порівнюються через один код прийняття рішення**: спільними
лишаються гіпотези, метрики й held-out критерій, а не сирі числові margin
різних scorer. Тобто порівнювати можна **вироки** (correct / wrong metre /
wrong phase / withheld), і не можна — стовпчики margin поруч.

Кількість значень мусить точно збігатися з кількістю бітів; розбіжність — це
помилка, а не привід вирівнювати наздогад.

## Чого тут свідомо немає

**ONNX Runtime у C++.** Дві причини, обидві навмисні. Інтерфейс бекенда варто
проєктувати над двома робочими реалізаціями, а не однією уявною — зараз робоча
одна (підказки), а шлях через salience-файл дає моделі оцінюватися без другої.
І ORT тут неможливо навіть скомпілювати — його бінарники за тим самим
заблокованим проксі. Коли артефакти будуть закріплені й виміряні через eval,
обгортка ORT стане окремою збиральною одиницею `tiktak_onnx` за прецедентом
`tiktak_decode` (`TIKTAK_BUILD_ONNX=OFF` за замовчуванням).

**Порівняння моделей на синтетиці.** Salience-шлях знімає технічну перепону,
але не статистичну: 13 синтетичних кліпів не розрізнять дві пристойні моделі.
Порівнювати є сенс на групово розділеному наборі приблизно з 200–300
незалежних реальних груп; окремих уривків може знадобитися більше — див.
`research/eval/README.md`, розділ про 95%-межі Wilson.
