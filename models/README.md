# Артефакти моделей

Тут живуть ваги моделей — а точніше, тут живе **облік** ваг: `manifest.json` з
закріпленими SHA-256, джерелами й ліцензіями. Самі файли в git не потрапляють
(`.gitignore` поруч), бо 97 МБ ONNX в історії — це назавжди; репозиторій
фіксує, *яким байтам довіряємо*, а не байти.

Ліцензії й джерела перевірені в [`docs/ml-models.md`](../docs/ml-models.md).
Коротко: BeatNet — CC BY 4.0 (продукт, онлайн), Beat This! — MIT включно з
вагами (офлайн-аналіз і псевдо-мітки).

## Чому такий обхідний шлях

Середовище розробки не має мережі: проксі ріже GitHub-релізи й huggingface.
Тому контрольну суму звідси закріпити неможливо, а сума, «пригадана» чи
переписана з вебсторінки — це вгадування у шістнадцятковому записі. Замість
цього — **довіра при першому отриманні**: перший успішний `pin` на машині з
мережею обчислює хеш і записує його в маніфест; коміт цієї зміни і є актом
поруки за артефакт. Кожен наступний `verify` тримає файл за той хеш.

Від чого це захищає — не від цільової атаки, а від буденного: повторне
завантаження, що тихо принесло інший файл; проксі, що віддав сторінку помилки
зі статусом 200; share-посилання, вміст якого з'їхав. Скрипт відмовляється
закріплювати HTML під виглядом моделі й розмір, що розходиться з задокументованим
на порядок.

```
python models/fetch.py list
python models/fetch.py pin beatnet_model_1 /шлях/до/model_1_weights.pt
python models/fetch.py pin beat_this_small https://…      # спершу завантажить
python models/fetch.py verify                              # тримає за хеш
```

Тільки stdlib — скрипт запускається на будь-якій машині з мережею без
установлення чогось.

## Як оцінити модель до того, як портувати її

Це найважливіше, що вміє цей етап, і працює воно вже зараз, без ONNX Runtime
у C++. Шов описано в `core/src/analysis/downbeat.hpp`: скоринг «наскільки ця
доля схожа на межу такту» відділений від резолвера «який розмір і фаза з цього
випливають». `dump_analysis --salience <file>` подає в **той самий** резолвер,
що працює в застосунку, зовнішню пер-бітову виразність:

```python
from eval.analysis import Analyser

analyser = Analyser()
grid = analyser.analyse_file("song.mp3")            # прохід 1: сітка бітів
activation = model_activation_at(grid.beats)        # модель, семпльована в бітах
result = analyser.analyse_file("song.mp3", salience=activation)
```

`result` має ті самі поля, ті самі margin'и в тих самих одиницях (резолвер
стандартизує виразність у себе — див. коментар до `resolveMeter`), і його
оцінює той самий `research/eval`. Тобто **дві моделі порівнюються між собою і з
базовими підказками через один код прийняття рішення** — інакше порівняння
вимірювало б різницю резолверів, а не моделей.

Кількість значень мусить точно збігатися з кількістю бітів; розбіжність — це
помилка, а не привід вирівнювати наздогад.

## Чого тут свідомо немає

**ONNX Runtime у C++.** Дві причини, обидві навмисні. Інтерфейс бекенда варто
проєктувати над двома робочими реалізаціями, а не однією уявною — зараз робоча
одна (підказки), а шлях через salience-файл дає моделі оцінюватися без другої.
І ORT тут неможливо навіть скомпілювати — його бінарники за тим самим
заблокованим проксі. Коли артефакти будуть закріплені й виміряні через eval,
обгортка ORT стане окремою збиральною одиницею `tiktak_onnx` за прецедентом
`tiktak_decode` (`TIKTAK_BUILD_ONNX=OFF` за замовчуванням).

**Порівняння моделей на синтетиці.** Salience-шлях знімає технічну перепону,
але не статистичну: 13 синтетичних кліпів не розрізнять дві пристойні моделі.
Порівнювати є сенс на розміченому наборі зі 100–150 записів —
див. `research/eval/README.md`, розділ про правило трьох.
