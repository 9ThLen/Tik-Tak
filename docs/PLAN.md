# tik-tak — план реалізації

Метроном, який **сам знаходить такт у музиці** — з файлу або з мікрофона.
Візуальна, тактильна та звукова підказка, коли починається доля і коли починається такт.

iOS першим, Android після нього, спільне ядро на C++.

## 1. Що саме будуємо

### Зафіксовані вимоги

| Параметр | Рішення |
|---|---|
| Платформи | iOS спершу, Android потім — спільне ядро на C++ |
| Цільові сценарії | спів під мінусовку, гра на інструменті, репетиція гурту |
| Джерела звуку | **імпортований файл** і мікрофон |
| Глибина аналізу | біти + сильна доля (downbeat) + розмір (4/4, 3/4, 6/8) |
| Канали підказки | візуально + вібрація + звук, кожен вмикається окремо |
| Обробка | повністю на пристрої, офлайн |

### Три режими роботи

**Файл** — користувач імпортує мінусовку, застосунок розбирає її повністю (з доступом
до всього треку наперед), будує точну сітку долей і тактів, і далі програє трек разом
із метрономом по цій сітці.

**Auto (мікрофон)** — застосунок слухає, визначає темп, фазу долі, сильну долю і розмір
у реальному часі; метроном іде за живою музикою і тримається за нею при дрейфі темпу.

**Manual + sync** — користувач задає BPM вручну (слайдер або tap-tempo), але застосунок
слухає, щоб **зловити початок мелодії** і вирівняти фазу кліку під неї. Період відомий,
шукаємо лише зсув — задача набагато простіша за Auto, тому цей режим працює майже
завжди. У UI він має бути рівноправним, а не «запасним».

**Поділ долі** — коли біти знайдено, субподіл на 2/3/4 тривіальний: додаткові кліки
між долями з іншим тембром, акцент на сильній долі.

### Чому режим «Файл» — головний, а не додатковий

Ваш основний сценарій — спів під мінусовку. Якщо мінусовка є файлом, слухати її через
мікрофон безглуздо: ми додаємо шум кімнати, реверберацію, затримку динаміка і ризик
помилки детекції там, де можна мати **точну відповідь за побудовою**. Розібрали файл
раз → сітка долей відома назавжди → метроном і трек синхронні ідеально.

Мікрофон потрібен там, де файлу немає: репетиція гурту, гра на живому інструменті,
чужа музика в приміщенні. Це справжня і цінна фіча — але вона обслуговує **другий**
за важливістю сценарій, і вона ж технічно найризикованіша. Тому в дорожній карті
файловий шлях іде раніше.

## 2. Ключові технічні рішення

**Ядро аналізу — портативний C++, платформи — тонкі оболонки.**
Оскільки Android у планах, писати DSP двічі (vDSP на Swift, потім наново на Kotlin/JNI)
було б грубою помилкою. Уся математика — один код на C++17 без залежностей від платформи.

**Усе на пристрої.** Сервер додав би 100–300 мс мережевої затримки до задачі, де бюджет
похибки — 20 мс. Плюс репетиція в підвалі без інтернету має працювати.

**Гібрид DSP + ML, а не чистий ML.**
- DSP (onset detection → оцінка темпу → трекінг фази) дає результат за ~10 мс, працює
  одразу, майже не їсть батарею, не має «холодного старту».
- ML вмикається лише там, де DSP справді слабкий: **сильна доля і розмір**. Визначити,
  що ось цей біт із чотирьох — перший, спектральними евристиками виходить на ~60–70%;
  невелика мережа дає 85–90%.

**Два трекери на спільному фронт-енді.** Онлайн (мікрофон, particle filter, працює
з випередженням) і офлайн (файл, динамічне програмування з повним оглядом уперед).
Обчислення ознак — той самий код. Офлайн-трекер помітно точніший, бо бачить майбутнє.

**Прототип на Python → порт у C++.** Ітерувати над алгоритмом без можливості швидко
прогнати 200 тестових файлів — марна трата тижнів. Доводимо метрики на Python,
потім переписуємо, звіряючи вихід на тих самих файлах.

## 3. Крос-платформенна архітектура

```
┌──────────────────────┐     ┌──────────────────────┐
│  iOS                 │     │  Android             │
│  SwiftUI             │     │  Jetpack Compose     │
│  AVAudioEngine       │     │  Oboe (AAudio)       │
│  CoreHaptics         │     │  VibrationEffect     │
│  AVAssetReader (m4a) │     │  MediaCodec (m4a)    │
└──────────┬───────────┘     └──────────┬───────────┘
           │  C API                     │  C API через JNI
           └────────────┬───────────────┘
                        ▼
        ┌───────────────────────────────────┐
        │   tiktak-core  (C++17, портативний)│
        │                                    │
        │   • STFT / мел-банк / ODF   (PFFFT)│
        │   • оцінка темпу                   │
        │   • онлайн-трекер (particle filter)│
        │   • офлайн-трекер (DP + HMM)       │
        │   • downbeat + розмір (ONNX Runtime)│
        │   • декодування mp3/wav/flac (dr_libs)│
        │   • планувальник долей             │
        └───────────────────────────────────┘
```

### Межа — плоский C API, не C++ ABI

```c
typedef struct tt_tracker tt_tracker;

tt_tracker* tt_tracker_create(const tt_config* cfg);
void        tt_tracker_destroy(tt_tracker*);

// Реалтайм: згодувати блок семплів, отримати прогноз наступних долей
tt_result   tt_tracker_process(tt_tracker*, const float* samples,
                               size_t n, double host_time_sec);
size_t      tt_tracker_pending_beats(const tt_tracker*, tt_beat* out, size_t cap);

// Офлайн: розібрати весь буфер, повернути сітку
tt_grid*    tt_analyze_offline(const float* samples, size_t n, double sample_rate);
```

Плоский C робить обидва боки дешевими: Swift викликає його напряму через module map
(Objective-C++ не потрібен), Android — через JNI-обгортку або напряму з JNI-функцій.
Стабільний ABI також означає, що ядро можна оновлювати незалежно від UI.

### Що лишається платформенним і чому

| Компонент | iOS | Android | Чому не спільне |
|---|---|---|---|
| Захоплення/відтворення | AVAudioEngine | **Oboe** | API реального часу принципово різні |
| Вібрація | CoreHaptics | VibrationEffect | різні моделі патернів |
| Вибір файлу | UIDocumentPicker | Storage Access Framework | системний UI |
| Декодування m4a/aac | AVAssetReader | MediaCodec | апаратні декодери |
| UI | SwiftUI | Compose | див. нижче |

**Oboe** для Android — не опція, а необхідність: це офіційна обгортка Google над
AAudio/OpenSL ES, яка вирівнює поведінку між пристроями і дає низьку затримку там,
де вона взагалі досяжна.

### Заміни Apple-специфічних бібліотек

| Було (тільки iOS) | Стало (портативно) | Коментар |
|---|---|---|
| `vDSP` FFT | **PFFFT** | BSD, SIMD через NEON/SSE, за швидкістю близький до vDSP |
| `CoreML` | **ONNX Runtime Mobile** | CoreML EP на iOS, NNAPI/XNNPACK на Android — одна модель, один API |
| `AVAudioFile` | **dr_libs** (`dr_mp3`/`dr_wav`/`dr_flac`) | public domain, один заголовок; m4a лишається платформенним |

Інтерфейс FFT усе одно тримаємо абстрактним — якщо профілювання покаже, що vDSP
відчутно швидший, підміна буде однорядковою.

### UI: нативний на обох, а не спільний

Аргумент проти Flutter/RN раніше був «аудіо-рушій усе одно доведеться писати нативно».
Тепер це вже не аргумент — ядро й так на C++, і Flutter звертався б до нього через FFI
так само добре.

Але UI метронома **дуже маленький**: пульсуючий індикатор, регулятор BPM, вибір розміру,
кілька перемикачів, екран імпорту. Дублювати таку поверхню дешевше, ніж тягнути весь
тулчейн Flutter і боротися з його шаром рендерингу заради єдиної речі, яка тут по-справжньому
важлива — кадрово точної анімації долі, синхронної з аудіо-годинником.

**Рекомендація: SwiftUI + Compose.** Рішення варте перегляду, якщо UI розростеться.

### Порядок

Android **не** будується паралельно з iOS. Але ядро від першого дня компілюється під
обидві платформи в CI — так воно ніколи випадково не обросте Apple-залежностями.
Сам Android-застосунок стартує, коли iOS дійде до стабільного стану.

## 4. Аудіо-конвеєр

```

    │  48 kHz mono, блок 512 семплів (~10.7 мс)
    ▼
┌─────────────────┐
│  Ring buffer    │  lock-free, без алокацій в audio thread
└────────┬────────┘
         ▼
┌─────────────────────────────────────────┐
│  Feature extraction        (спільний C++)│
│  • STFT: вікно 2048, хоп 512 (~93 fps)  │
│  • мел-банк 81 смуга, log-магнітуда     │
│  • adaptive whitening                    │
│  • spectral flux, half-wave rectified   │
│    → ODF (onset detection function)     │
│  • окремо низька смуга (<200 Гц) — бочка│
└────────┬────────────────────────────────┘
         │
    ┌────┴──────────────────┬─────────────────────┐
    ▼                       ▼                     ▼
┌──────────────┐  ┌────────────────────┐  ┌──────────────────┐
│ Оцінка темпу │  │ ТРЕКЕР ФАЗИ        │  │ ONNX: downbeat   │
│ автокореляція│─▶│ онлайн: particle   │─▶│ + розмір такту   │
│ 40–220 BPM   │  │   filter (прогноз) │  │ (beat-synchronous│
│ + пріор      │  │ офлайн: DP + HMM   │  │  ознаки)         │
└──────────────┘  │   (повний огляд)   │  └────────┬─────────┘

                            ▼                      ▼
                  ┌──────────────────────────────────────┐
                  │  Beat Clock — єдине джерело часу     │
                  └───┬──────────┬──────────┬────────────┘
                      ▼          ▼          ▼
                  аудіо-клік  вібрація   екран
                  (−outputLatency) (−~15мс) (−1 кадр)
```

Критично: три канали виводу мають **різні власні затримки**, тож кожен планується
зі своїм зсувом від спільного часу долі. Інакше вібрація «пливе» відносно кліку.

### Налаштування сесії

**iOS:**
```swift
category: .playAndRecord
mode:     .measurement          // вимикає AGC — потрібен чистий сигнал
setPreferredIOBufferDuration(0.005)
setPreferredSampleRate(48000)
```
`.measurement` принципово важливий: інакше iOS вмикає автоматичне регулювання
підсилення, яке «дихає» і псує криву onset'ів.

**Android:** Oboe у режимі `PerformanceMode::LowLatency`, `SharingMode::Exclusive`,
`InputPreset::Unprocessed` (аналог `.measurement` — вимикає обробку голосу).

## 5. Алгоритм

### 5.1 Onset detection function — спільна для всіх режимів

Спектральний потік: різниця log-мел-спектра між сусідніми кадрами з напівхвильовим
випрямленням (враховуємо лише зростання енергії):

```
ODF[n] = Σ_k max(0, log|X[n,k]| − log|X[n−1,k]|)
```

Adaptive whitening перед цим нормалізує кожну смугу за ковзним максимумом — щоб тиха
гітара і гучні барабани давали співмірний внесок.

Тримаємо **три ODF паралельно**: повносмуговий, низький (<200 Гц — бочка/бас, найкращий
маркер сильної долі), високий (>4 кГц — хет, найкращий маркер субподілу).

### 5.2 Оцінка темпу

Автокореляція ODF на вікні 6–8 с (онлайн) або по всьому треку (офлайн). Пік = період долі.

Дві обов'язкові поправки:
- **Лог-нормальний пріор** із центром ~120 BPM — інакше алгоритм систематично плутає
  темп удвічі (60 замість 120, 240 замість 120). Це найпоширеніша помилка beat-трекерів.
- На виході — **розподіл імовірності по періодах**, не одне число.

### 5.3 Онлайн-трекер — particle filter

Стан: `(період, фаза)`. Кілька сотень частинок.

- **Predict** — кожна частинка рухає фазу вперед, період отримує невелике випадкове
  збурення (моделює rubato й природний дрейф).
- **Update** — вага частинки ∝ значення ODF у момент, коли вона передбачає долю.
- **Resample** — систематичний ресемплінг за вагами.
- **Вихід** — **прогноз часу наступної долі** + впевненість.

Чому не динамічне програмування (класика Ellis 2007): DP потребує всього сигналу
наперед. Онлайн треба **з випередженням** — клік мусить прозвучати рівно в момент долі,
тобто рішення ухвалюється за 50–100 мс до неї. Трекер має не *детектувати* долю,
а *передбачати* її.

Впевненість іде в UI: коли вона падає (тиша, шум, зміна пісні), метроном не смикається,
а продовжує за останнім надійним темпом і показує це користувачу.

### 5.4 Офлайн-трекер — динамічне програмування

Для файлу обмеження реального часу зникає, і можна взяти помітно точніший підхід:

1. Глобальна оцінка темпу по всьому треку (стійкіша за віконну).
2. Динамічне програмування по всій ODF: шукаємо послідовність долей, яка максимізує
   `Σ ODF(bᵢ) + λ · Σ штраф_за_відхилення_інтервалу(bᵢ − bᵢ₋₁)`. Класичний Ellis 2007,
   оптимальний розв'язок за один прохід уперед і зворотний трасинг.
3. Для змінного темпу — HMM/DBN над станами `(період, позиція в такті)` замість
   фіксованого періоду.
4. Сильна доля — **двонаправлена** модель: офлайн можна дивитися і вперед, і назад,
   що дає відчутно кращий результат, ніж однобічний онлайн.

Побічна користь: офлайн-трекер стає **джерелом еталонів для перевірки онлайн-трекера**
на власних записах — не треба розмічати все руками.

### 5.5 Сильна доля і розмір

Для кожної знайденої долі збираємо beat-synchronous ознаки:
- енергія низької смуги (бочка майже завжди на 1-й долі),
- зміна хроми — гармонія найчастіше змінюється саме на межі такту,
- величина ODF,
- позиція відносно попередніх сильних доль.

Мережа видає `P(downbeat | beat)` + класифікацію розміру. Поверх — марковське
згладжування: якщо розмір 4/4, сильна доля йде рівно кожні 4 долі, і одиничний сплеск
ймовірності її не зсуває.

### 5.6 Manual + sync

Період відомий — шукаємо лише фазу.
1. Перший onset понад адаптивний поріг → «музика почалась».
2. Крос-кореляція ODF за останні 2–3 с із гребінкою імпульсів заданого періоду.
3. Максимум кореляції = зсув фази. Одна цифра, миттєво.
4. Далі фазу тримає той самий particle filter із **зафіксованим періодом** — компенсує
   лише дрейф виконавця.

## 6. Офлайн-аналіз файлів

### Конвеєр

```
файл → декодування → моно 48 кГц → ODF → глобальний темп
     → DP-трекінг долей → двонаправлений downbeat + розмір
     → сітка долей → кеш на диску (JSON/бінарно, ключ = хеш файлу)
```

Розбір робиться **один раз** і кешується. Трихвилинний трек на сучасному телефоні —
одиниці секунд; у UI це прогрес-бар при імпорті, далі миттєво.

### Декодування

| Формат | Як | Де |
|---|---|---|
| mp3, wav, flac, ogg | `dr_libs` / `stb_vorbis` | у ядрі, портативно |
| m4a, aac | AVAssetReader / MediaCodec | платформенно |

### ⚠️ Обмеження, яке треба знати заздалегідь

**Треки з Apple Music, Spotify та інших стримінгів прочитати неможливо.** Вони захищені
DRM, і жоден API не дасть до них доступ як до сирого аудіо. Це не обхідна проблема —
це навмисне обмеження платформ.

Працюють: власні файли користувача (Files / Downloads), незахищені покупки, експортовані
мінусовки, записи з диктофона. У UI це треба пояснити м'яко й одразу, бо інакше перше,
що зробить користувач — спробує додати трек із Apple Music і вирішить, що застосунок
зламаний.

Часткова компенсація: якщо стримінг грає з іншого застосунку **вголос**, працює
мікрофонний режим Auto. Гірше за файл, але не глухий кут.

### Що це відкриває

Коли трек розібрано і програється з застосунку, ми знаємо позицію відтворення **точно**.
Це прибирає з основного сценарію всю невизначеність детекції — і додатково дає:
- перемотування по тактах, а не по секундах;
- зациклення складного місця рівно по межах такту;
- відлік «раз-два-три-чотири» перед вступом;
- зміну темпу треку без зміни висоти (time-stretch) для повільного розучування;
- у Фазі «зворотний зв'язок» — порівняння голосу з еталонною сіткою, а не з оцінкою.

## 7. Точність часу

Найчастіша причина, чому саморобні метрономи «плавають».

**Ніколи не грати клік по команді.** `play()` у момент долі дає джитер 20–50 мс.
Кліки **плануються наперед** у майбутньому часі:

```swift
let when = AVAudioTime(hostTime: beatHostTime - outputLatencyInHostTicks)
player.scheduleBuffer(clickBuffer, at: when, options: [])
```

Планувальник тримає чергу на 2–3 долі вперед і переписує її, якщо трекер змінив оцінку.

**Один годинник на все.** Уся система в одному часовому домені (`mach_absolute_time`
на iOS, `CLOCK_MONOTONIC` на Android). Час приходу семпла беремо з таймстемпа
аудіо-колбека, а не з системного годинника.

**Компенсація затримок:**

| Канал | iOS | Android |
|---|---|---|
| вхід | 5–30 мс | 10–100 мс, дуже різниться |
| вихід | 10–40 мс (BT: до 200) | 20–150 мс, дуже різниться |
| вібрація | ~10–20 мс | 20–50 мс, різниться |
| екран | 1 кадр (8–16 мс) | 1 кадр |

**Android — окрема історія.** Затримка там гірша й значно менш передбачувана, ніж на iOS.
Oboe дає найкраще з можливого, `AudioManager.getOutputLatency` бреше на багатьох
пристроях. Тому **екран калібрування на Android обов'язковий**, а не опційний:
користувач стукає в такт із кліком, ми вимірюємо його систематичний зсув і компенсуємо.
На iOS той самий екран лишається опційним — для Bluetooth-навушників.

**Цільові показники (iOS):**
- джитер кліку < 2 мс,
- похибка позиції долі відносно еталону < 20 мс,
- затримка «зміна темпу → підлаштування» < 2 с.

Для Android цілі встановлюємо після замірів на реальних пристроях — обіцяти ті самі
цифри наперед було б нечесно.

## 8. Проблема зворотного зв'язку

Оскільки звук у динамік увімкнено (за бажанням користувача), мікрофон чує власний клік.
Без запобіжника трекер захоплюється власним сигналом і «підтверджує» будь-який
неправильний темп, у який один раз влучив.

**Рішення — часове стробування, а не повна ехо-компенсація.** Ми точно знаємо, коли
пролунає клік (самі його запланували), і він короткий (~30 мс). Тож просто **не оновлюємо
ODF у вікні ±40 мс навколо кожного власного кліку**. На 120 BPM це ~15% викинутих
кадрів — трекер це переживає без проблем.

Це краще за вбудовану ехо-компенсацію (`setVoiceProcessingEnabled` / `AcousticEchoCanceler`):
вона розрахована на мову, застосовує агресивну фільтрацію й AGC і псує сигнал саме
в потрібному нам діапазоні.

Те саме стробування працює й для звуку мінусовки, якщо вона грає з динаміка, — але
там ми знаємо весь сигнал наперед, тож за потреби можна зробити й повноцінне віднімання.

Вібрація й візуал від цієї проблеми вільні взагалі — для співака на репетиції це,
ймовірно, взагалі кращий основний канал.

## 9. ML-моделі

### Що ставимо в застосунок

Орієнтир — **BeatNet** (Heydari et al., ISMIR 2021): «CRNN and Particle Filtering for
Online Joint Beat, Downbeat and Meter Tracking». Це буквально формулювання нашої задачі:
онлайн, спільно біти + сильна доля + розмір. Мережа маленька (сотні тисяч параметрів),
на виході — ймовірності, які подаються в particle filter.

Шлях у застосунок: PyTorch → **ONNX** → ONNX Runtime Mobile.
Один артефакт моделі на обидві платформи; апаратне прискорення через execution providers
(CoreML на iOS, NNAPI/XNNPACK на Android). Якщо профілювання покаже, що на iOS
конвертація в `.mlpackage` дає відчутний виграш — можна возити два артефакти з одного
ONNX, але починаємо з одного.

### Що використовуємо лише в дослідженні

- **madmom** — `RNNDownBeatProcessor` + `DBNDownBeatTrackingProcessor`, багато років
  еталон точності. Офлайн: генерувати псевдо-розмітку для власних записів і як стелю,
  з якою порівнюємось.
  ⚠️ **Ліцензія — перевірити перед комерційним використанням.** BSD-подібна з окремим
  застереженням щодо комерційного застосування. Для дослідження питань немає,
  у продукт не тягнемо.
- **Beat-Transformer**, **All-In-One** (`taejunkim/allinone` на HuggingFace) — офлайнові,
  важчі, дуже точні на сильній долі. Джерело псевдо-міток і референс.
  Окремо варто перевірити, чи не підходить щось із них прямо для нашого офлайн-режиму —
  там обмежень реального часу немає, і можна дозволити собі більшу модель.

### Чесне зауваження

Точні ідентифікатори репозиторіїв і поточні ліцензії треба **перевірити на місці** —
наводжу по пам'яті, екосистема рухається. Перший крок дослідницької фази — верифікація
доступності, ліцензій і розмірів, і лише потім вибір.

## 10. Оцінка якості

Без вимірювання цю задачу зробити неможливо — «на слух здається, що працює» розвалюється
на першому ж вальсі.

**Метрики** (стандарт MIREX, `mir_eval.beat`):
- **F-measure** з допуском ±70 мс — основна;
- **CMLt / AMLt** — неперервність трекінгу, причому AMLt пробачає помилку в октаві темпу,
  що показує, які саме помилки ми робимо;
- окремо **downbeat F-measure** — він завжди помітно гірший за beat F-measure.

Метрики рахуються **окремо для офлайн- і онлайн-трекера**. Офлайн має бути відчутно
кращим; якщо ні — щось зламано.

**Дані:**
- публічні набори з розміткою: Ballroom, Hainsworth, SMC, GTZAN-Rhythm (частина потребує
  запиту на доступ — закласти час);
- **власний набір** — критично: 30–50 записів саме у ваших умовах. Спів під мінусовку
  з телефона, гітара в кімнаті, репетиція гурту, шумне приміщення. Публічні набори
  складаються зі студійних записів і систематично завищують очікування.

**Тест на регресію часу** — окремо від якості алгоритму: прогін метронома на пристрої
з записом власного виходу через аудіо-інтерфейс і вимірюванням реального джитера.
Ловить помилки планування, яких не видно в Python. На Android — на кількох різних
пристроях, бо розкид великий.

## 12. Дорожня карта

### Фаза 0 — Фундамент
Каркас `core/` на CMake, плоский C API, CI, що збирає ядро **під iOS і Android від
першого дня**, каркас Xcode-проєкту, базовий SwiftUI-скелет.
*Результат: порожній застосунок збирається, ядро лінкується, Android-збірка ядра зелена.*

### Фаза 1 — Бездоганний ручний метроном (iOS)
Семплово-точне планування, три канали виводу з окремою компенсацією затримок,
розміри 2/4–7/8, субподіли, tap-tempo, акцент на сильній долі.
*Результат: самодостатній застосунок, який уже можна віддати людям.*
Навмисно перша: якщо тайминг зламаний, детекція такту нічого не врятує.

### Фаза 2 — Дослідження (Python)
ODF, оцінка темпу, **офлайн-трекер (DP)**, harness на `mir_eval`, публічні набори,
збір власного набору. Верифікація моделей і ліцензій із розділу 9.
*Результат: цифри F-measure/CMLt на реальних даних до першого рядка C++.*

### Фаза 3 — Імпорт файлу й офлайн-аналіз
Порт ODF + офлайн-трекера у C++. Декодування, UI імпорту, кеш сітки, прогрес-бар.
*Результат: користувач додає мінусовку — застосунок показує її темп, долі й такти.*

### Фаза 4 — Відтворення з метрономом
Програвання треку синхронно з метрономом по знайденій сітці. Відлік перед вступом,
зациклення по тактах, перемотування по тактах.
*Результат: **головний сценарій закрито повністю** — і без жодного ризику детекції.*

### Фаза 5 — Реалтайм із мікрофона
Порт онлайн-трекера (particle filter) у C++. Стробування власного кліку. Режим Auto.
*Результат: працює репетиція гурту й живий інструмент.*
Звірка C++↔Python на тих самих файлах — обов'язковий вихідний критерій фази.

### Фаза 6 — Manual + sync
Детекція початку мелодії, вирівнювання фази при заданому вручну BPM.

### Фаза 7 — Сильна доля і розмір
Тренування/конвертація мережі, ONNX Runtime, марковське згладжування.
Спершу для офлайн (двонаправлена, точніша), потім онлайн.

### Фаза 8 — Зворотний зв'язок співаку
Порівняння онсетів голосу з сіткою долей → «ви стабільно поспішаєте на 40 мс».
Статистика по сесії, прогрес.
*Це те, що відрізняє застосунок від сотні метрономів у App Store.*

### Фаза 9 — Android
Compose-UI, Oboe, JNI-обгортка, обов'язкове калібрування затримки, тестування на
кількох пристроях.
*Ядро вже готове й перевірене — це переважно робота з платформою, не з алгоритмами.*

### Фаза 10 — Реліз
Онбординг, доступність, App Store і Google Play.

**Оцінка часу.** Фази 0–1 — 3–4 тижні (C++-каркас додає до попередньої оцінки).
Фази 2–4 — 2–2.5 місяця, головна маса роботи. Фази 5–7 — ще 2 місяці, найбільша
невизначеність саме тут. Фази 8–10 — 1.5–2 місяці, з яких Android сам по собі
3–5 тижнів. Разом реалістично **7–9 місяців** для однієї людини в нормальному темпі.
Цифри сильно залежать від вашого досвіду в C++ і DSP.

## 14. Розподіл праці

**Що робиться в цьому контейнері (Linux):**
- уся папка `research/` — прототип на Python, harness, експерименти, звіти з метриками;
- **`core/` — повністю**: C++ пишеться, збирається і тестується тут нативно (googletest,
  CMake). Це велика частина проєкту, і вона перевіряється по-справжньому, а не наосліп;
- скрипти конвертації моделей, `docs/`, ADR;
- **написання** Swift/Kotlin-коду.

**Що потрібно робити на вашому боці:**
- збірка Xcode/Android Studio, запуск на пристроях;
- усе, що стосується вимірювання реальних затримок і джитера;
- профілювання, TestFlight, реліз.

Винесення ядра в C++ дало побічний плюс: **більшу частину логіки тепер можна повноцінно
розробляти й тестувати тут**. Раніше весь DSP на vDSP був би непротестованим до вашої
збірки. Тепер непротестованими лишаються лише тонкі платформенні оболонки.

## Відкриті питання

1. **UI: SwiftUI + Compose нативно, чи спільний Flutter?** Моя рекомендація — нативно
   (поверхня UI мала, а кадрово точна анімація долі важлива). Рішення потрібне на початок
   Фази 1.
2. **Комерційний застосунок чи для себе?** Впливає на вибір ліцензій моделей і на те,
   чи закладати монетизацію в архітектуру одразу.
3. **Наскільки ви впевнено почуваєтесь у C++, DSP і ML?** Від цього залежить, наскільки
   детально коментувати код і чи писати пояснювальні документи до кожного алгоритму.
4. **Android — одразу після iOS чи «колись»?** Ядро й CI готуємо однаково в обох випадках,
   але від відповіді залежить, наскільки рано інвестувати в JNI-шар і тестові пристрої.
