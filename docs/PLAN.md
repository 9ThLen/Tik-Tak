# tik-tak — план реалізації

Метроном, який **сам знаходить такт у музиці** — з файлу або з мікрофона.
Візуальна, тактильна та звукова підказка, коли починається доля і коли починається такт.

iOS — цільова платформа, Android після нього, спільне ядро на C++.

> **Обмеження середовища розробки.** Робоча машина — Windows, цільовий пристрій — iPhone.
> Xcode є лише під macOS, тож iOS збирається в CI, а на пристрій потрапляє лише через
> TestFlight. Тому основна робота ведеться на **настільному стенді під Windows** поверх
> того самого ядра — див. [ADR 0003](adr/0003-windows-host-no-mac.md). Це змінює порядок
> фаз, але не архітектуру.

## 1. Що саме будуємо

### Зафіксовані вимоги

| Параметр | Рішення |
|---|---|
| Платформи | iOS (ціль), Android потім — спільне ядро на C++ |
| Середовище розробки | Windows + iPhone; основна робота на настільному стенді (ADR 0003) |
| Цільові сценарії | спів під мінусовку, гра на інструменті, репетиція гурту |
| Джерела звуку | **імпортований файл** і мікрофон |
| Глибина аналізу | біти + сильна доля (downbeat) + розмір (4/4, 3/4, 6/8) |
| Канали підказки | візуально + вібрація + звук, кожен вмикається окремо |
| Обробка | повністю на пристрої, офлайн |

### Три режими роботи

**Файл** — користувач імпортує мінусовку, застосунок розбирає її повністю (з доступом
до всього треку наперед), будує точну сітку долей і тактів, і далі програє трек разом
із метрономом по цій сітці.

**Auto (мікрофон)** — застосунок слухає, визначає темп, фазу долі, сильну долю і розмір
у реальному часі; метроном іде за живою музикою і тримається за нею при дрейфі темпу.

**Manual + sync** — користувач задає BPM вручну (слайдер або tap-tempo), але застосунок
слухає, щоб **зловити початок мелодії** і вирівняти фазу кліку під неї. Період відомий,
шукаємо лише зсув — задача набагато простіша за Auto, тому цей режим працює майже
завжди. У UI він має бути рівноправним, а не «запасним».
*Реалізовано у Фазі 5–6; ціною за «працює майже завжди» є те, що режим уміє
відмовитись, коли заданої долі в кімнаті немає.*

**Поділ долі** — коли біти знайдено, субподіл на 2/3/4 тривіальний: додаткові кліки
між долями з іншим тембром, акцент на сильній долі.

### Чому режим «Файл» — головний, а не додатковий

Ваш основний сценарій — спів під мінусовку. Якщо мінусовка є файлом, слухати її через
мікрофон безглуздо: ми додаємо шум кімнати, реверберацію, затримку динаміка і ризик
помилки детекції там, де можна мати **точну відповідь за побудовою**. Розібрали файл
раз → сітка долей відома назавжди → метроном і трек синхронні ідеально.

Мікрофон потрібен там, де файлу немає: репетиція гурту, гра на живому інструменті,
чужа музика в приміщенні. Це справжня і цінна фіча — але вона обслуговує **другий**
за важливістю сценарій, і вона ж технічно найризикованіша. Тому в дорожній карті
файловий шлях іде раніше.

## 2. Ключові технічні рішення

**Ядро аналізу — портативний C++, платформи — тонкі оболонки.**
Оскільки Android у планах, писати DSP двічі (vDSP на Swift, потім наново на Kotlin/JNI)
було б грубою помилкою. Уся математика — один код на C++17 без залежностей від платформи.

**Усе на пристрої.** Сервер додав би 100–300 мс мережевої затримки до задачі, де бюджет
похибки — 20 мс. Плюс репетиція в підвалі без інтернету має працювати.

**Гібрид DSP + ML, а не чистий ML.**
- DSP (onset detection → оцінка темпу → трекінг фази) дає результат за ~10 мс, працює
  одразу, майже не їсть батарею, не має «холодного старту».
- ML вмикається лише там, де DSP справді слабкий: **сильна доля і розмір**. Визначити,
  що ось цей біт із чотирьох — перший, спектральними евристиками виходить на ~60–70%;
  невелика мережа дає 85–90%.

**Два трекери на спільному фронт-енді.** Онлайн (мікрофон, particle filter, працює
з випередженням) і офлайн (файл, динамічне програмування з повним оглядом уперед).
Обчислення ознак — той самий код. Офлайн-трекер помітно точніший, бо бачить майбутнє.

**Прототип на Python → порт у C++.** Ітерувати над алгоритмом без можливості швидко
прогнати 200 тестових файлів — марна трата тижнів. Доводимо метрики на Python,
потім переписуємо, звіряючи вихід на тих самих файлах.

## 3. Крос-платформенна архітектура

```
┌──────────────────────┐     ┌──────────────────────┐
│  iOS                 │     │  Android             │
│  SwiftUI             │     │  Jetpack Compose     │
│  AVAudioEngine       │     │  Oboe (AAudio)       │
│  CoreHaptics         │     │  VibrationEffect     │
│  AVAssetReader (m4a) │     │  MediaCodec (m4a)    │
└──────────┬───────────┘     └──────────┬───────────┘
           │  C API                     │  C API через JNI
           └────────────┬───────────────┘
                        ▼
        ┌───────────────────────────────────┐
        │   tiktak-core  (C++17, портативний)│
        │                                    │
        │   • STFT / мел-банк / ODF   (PFFFT)│
        │   • оцінка темпу                   │
        │   • онлайн-трекер (particle filter)│
        │   • офлайн-трекер (DP + HMM)       │
        │   • downbeat + розмір (ONNX Runtime)│
        │   • планувальник долей             │
        └───────────────────────────────────┘
                        ▲
        ┌───────────────┴───────────────────┐
        │   tiktak-decode  (окрема ціль)     │
        │   • mp3 / wav / flac (dr_libs)     │
        └───────────────────────────────────┘
```

Декодування винесено з ядра **окремою бібліотекою**, і це принципово: `tiktak_core`
не має жодної сторонньої залежності, і саме ця властивість дозволяє йому збиратися
під будь-яку платформу без розмов про вендорінг. Декодування такої властивості мати
не може — йому потрібні реалізації кодеків. Платформа, яка хоче свій `AVAssetReader`
чи `MediaCodec`, лінкує лише ядро.

### Межа — плоский C API, не C++ ABI

```c
typedef struct tt_tracker tt_tracker;

tt_tracker* tt_tracker_create(const tt_config* cfg);
void        tt_tracker_destroy(tt_tracker*);

// Реалтайм: згодувати блок семплів, отримати прогноз наступних долей
tt_result   tt_tracker_process(tt_tracker*, const float* samples,
                               size_t n, double host_time_sec);
size_t      tt_tracker_pending_beats(const tt_tracker*, tt_beat* out, size_t cap);

// Офлайн: розібрати весь буфер, повернути сітку
tt_grid*    tt_analyze_offline(const float* samples, size_t n, double sample_rate);
```

Плоский C робить обидва боки дешевими: Swift викликає його напряму через module map
(Objective-C++ не потрібен), Android — через JNI-обгортку або напряму з JNI-функцій.
Стабільний ABI також означає, що ядро можна оновлювати незалежно від UI.

### Що лишається платформенним і чому

| Компонент | iOS | Android | Чому не спільне |
|---|---|---|---|
| Захоплення/відтворення | AVAudioEngine | **Oboe** | API реального часу принципово різні |
| Вібрація | CoreHaptics | VibrationEffect | різні моделі патернів |
| Вибір файлу | UIDocumentPicker | Storage Access Framework | системний UI |
| Декодування m4a/aac | AVAssetReader | MediaCodec | апаратні декодери |
| UI | SwiftUI | Compose | див. нижче |

**Oboe** для Android — не опція, а необхідність: це офіційна обгортка Google над
AAudio/OpenSL ES, яка вирівнює поведінку між пристроями і дає низьку затримку там,
де вона взагалі досяжна.

### Заміни Apple-специфічних бібліотек

| Було (тільки iOS) | Стало (портативно) | Коментар |
|---|---|---|
| `vDSP` FFT | **PFFFT** | BSD, SIMD через NEON/SSE, за швидкістю близький до vDSP |
| `CoreML` | **ONNX Runtime Mobile** | CoreML EP на iOS, NNAPI/XNNPACK на Android — одна модель, один API |
| `AVAudioFile` | **dr_libs** (`dr_mp3`/`dr_wav`/`dr_flac`) | public domain, один заголовок; m4a лишається платформенним |

Інтерфейс FFT усе одно тримаємо абстрактним — якщо профілювання покаже, що vDSP
відчутно швидший, підміна буде однорядковою.

### UI: нативний на обох, а не спільний

Аргумент проти Flutter/RN раніше був «аудіо-рушій усе одно доведеться писати нативно».
Тепер це вже не аргумент — ядро й так на C++, і Flutter звертався б до нього через FFI
так само добре.

Але UI метронома **дуже маленький**: пульсуючий індикатор, регулятор BPM, вибір розміру,
кілька перемикачів, екран імпорту. Дублювати таку поверхню дешевше, ніж тягнути весь
тулчейн Flutter і боротися з його шаром рендерингу заради єдиної речі, яка тут по-справжньому
важлива — кадрово точної анімації долі, синхронної з аудіо-годинником.

**Рекомендація: SwiftUI + Compose.** Рішення варте перегляду, якщо UI розростеться.

### Порядок

Android **не** будується паралельно з iOS. Але ядро від першого дня компілюється під
обидві платформи в CI — так воно ніколи випадково не обросте Apple-залежностями.
Сам Android-застосунок стартує, коли iOS дійде до стабільного стану.

```

    │  48 kHz mono, блок 512 семплів (~10.7 мс)
    ▼
┌─────────────────┐

└────────┬────────┘
         ▼

                  │  Beat Clock — єдине джерело часу     │

```

Критично: три канали виводу мають **різні власні затримки**, тож кожен планується
зі своїм зсувом від спільного часу долі. Інакше вібрація «пливе» відносно кліку.

### Налаштування сесії

**iOS:**
```swift
category: .playAndRecord
mode:     .measurement          // вимикає AGC — потрібен чистий сигнал
setPreferredIOBufferDuration(0.005)
setPreferredSampleRate(48000)
```
`.measurement` принципово важливий: інакше iOS вмикає автоматичне регулювання
підсилення, яке «дихає» і псує криву onset'ів.

**Android:** Oboe у режимі `PerformanceMode::LowLatency`, `SharingMode::Exclusive`,
`InputPreset::Unprocessed` (аналог `.measurement` — вимикає обробку голосу).

## 5. Алгоритм

### 5.1 Onset detection function — спільна для всіх режимів

Спектральний потік: різниця log-мел-спектра між сусідніми кадрами з напівхвильовим
випрямленням (враховуємо лише зростання енергії):

```
ODF[n] = Σ_k max(0, log|X[n,k]| − log|X[n−1,k]|)
```

Adaptive whitening перед цим нормалізує кожну смугу за ковзним максимумом — щоб тиха
гітара і гучні барабани давали співмірний внесок.

Тримаємо **три ODF паралельно**: повносмуговий, низький (<200 Гц — бочка/бас, найкращий
маркер сильної долі), високий (>4 кГц — хет, найкращий маркер субподілу).

### 5.2 Оцінка темпу

Автокореляція ODF на вікні 6–8 с (онлайн) або по всьому треку (офлайн). Пік = період долі.

Дві обов'язкові поправки:
- **Лог-нормальний пріор** із центром ~120 BPM — інакше алгоритм систематично плутає
  темп удвічі (60 замість 120, 240 замість 120). Це найпоширеніша помилка beat-трекерів.
- На виході — **розподіл імовірності по періодах**, не одне число.

**Гребінка по метричних кратностях: виміряна й відкинута.** Раніше в цьому плані
стояло, що підсумовування автокореляції по кратних періодах прибирає неметричні піки
й тому ввімкнене за замовчуванням. На 140 синтетичних кліпах (60–196 BPM) це виявилося
хибним — гребінка гірша за всіма метриками:

| гармонік | F | CMLt | AMLt | неметричних |
|---|---|---|---|---|
| 1 (вимкнено) | **0.900** | **0.702** | **0.991** | **0/140** |
| 3 | 0.889 | 0.681 | 0.977 | 2/140 |
| 4 | 0.880 | 0.660 | 0.970 | 4/140 |

Причому вона **вносила саме ту помилку, від якої мала рятувати**: кандидат на 2/3
істинного періоду отримує повну підтримку від кожної третьої кратності. Обмеження
гребінки степенями двійки не рятує (F 0.874).

Чому помилка сталася: попередній висновок спирався на 13 кліпів і на класифікацію
темпу як проксі, а не на метрику трекінгу. На тих самих 13 кліпах гребінка не змінює
взагалі нічого — F/CMLt/AMLt збігаються до третього знаку. Тобто підстави ніколи не
було видно у бенчмарку, і я прийняв її передчасно.

Параметр лишено в конфігурації, а не видалено: гребінка — стандартна практика в
літературі (Klapuri, Davies), а всі ці дані синтетичні й з одного генератора.
Переміряти на реальному розміченому матеріалі, перш ніж робити загальний висновок.

**Впевненість.** Спершу вона рахувалась як різкість піку відносно решти сітки. Це
міряло не те: білий шум дає різкий, але беззмістовний пік і отримував за цією мірою
0.76 — вище, ніж чистий біт із 0.84. Для інтерфейсу, чия задача — відрізнити «впевнено»
від «вгадую», це рівно навпаки. Тепер впевненість — це автокореляція на обраному
періоді як частка від дисперсії сигналу, тобто пряме питання «чи це взагалі
повторюється». Ті самі випадки: шум 0.02, реальні кліпи 0.76–0.92.

### 5.3 Онлайн-трекер — particle filter

Стан: `(період, фаза)`. Кілька сотень частинок.

- **Predict** — кожна частинка рухає фазу вперед, період отримує невелике випадкове
  збурення (моделює rubato й природний дрейф).
- **Update** — вага частинки ∝ значення ODF у момент, коли вона передбачає долю.
- **Resample** — систематичний ресемплінг за вагами.
- **Вихід** — **прогноз часу наступної долі** + впевненість.

Чому не динамічне програмування (класика Ellis 2007): DP потребує всього сигналу
наперед. Онлайн треба **з випередженням** — клік мусить прозвучати рівно в момент долі,
тобто рішення ухвалюється за 50–100 мс до неї. Трекер має не *детектувати* долю,
а *передбачати* її.

Впевненість іде в UI: коли вона падає (тиша, шум, зміна пісні), метроном не смикається,
а продовжує за останнім надійним темпом і показує це користувачу.

### 5.4 Офлайн-трекер — динамічне програмування

Для файлу обмеження реального часу зникає, і можна взяти помітно точніший підхід:

1. Глобальна оцінка темпу по всьому треку (стійкіша за віконну).
2. Динамічне програмування по всій ODF: шукаємо послідовність долей, яка максимізує
   `Σ ODF(bᵢ) + λ · Σ штраф_за_відхилення_інтервалу(bᵢ − bᵢ₋₁)`. Класичний Ellis 2007,
   оптимальний розв'язок за один прохід уперед і зворотний трасинг.
3. Для змінного темпу — HMM/DBN над станами `(період, позиція в такті)` замість
   фіксованого періоду.
4. Сильна доля — **двонаправлена** модель: офлайн можна дивитися і вперед, і назад,
   що дає відчутно кращий результат, ніж однобічний онлайн.

Побічна користь: офлайн-трекер стає **джерелом еталонів для перевірки онлайн-трекера**
на власних записах — не треба розмічати все руками.

### 5.5 Сильна доля і розмір

Для кожної знайденої долі збираємо beat-synchronous ознаки:
- енергія низької смуги (бочка майже завжди на 1-й долі),
- зміна хроми — гармонія найчастіше змінюється саме на межі такту,
- величина ODF,
- позиція відносно попередніх сильних доль.

Мережа видає `P(downbeat | beat)` + класифікацію розміру. Поверх — марковське
згладжування: якщо розмір 4/4, сильна доля йде рівно кожні 4 долі, і одиничний сплеск
ймовірності її не зсуває.

> **Як це вийшло насправді (Фаза 7, портативна половина).** Згладжування
> згорнулося в нуль. Якщо розмір сталий, сильна доля йде рівно кожні `M` долей
> **за визначенням**, тож зафіксувавши `M` і фазу, ми вже маємо всі межі такту:
> простір гіпотез — десяток пар, кожну оцінюємо точно, і згладжувати нічого.
> Марковський шар мав би сенс лише для змінного розміру, і саме тоді його треба
> буде повернути. Ознаки лишилися ті, що в списку вище, з одним виправленням від
> вимірювання: величина ODF як ознака сильної долі вказує на бекбіт, а не на
> першу долю, і за замовчуванням вимкнена. Деталі — у Фазі 7 дорожньої карти.

### 5.6 Manual + sync

Період відомий — шукаємо лише фазу.
1. Перший onset понад адаптивний поріг → «музика почалась».
2. Крос-кореляція ODF за останні 2–3 с із гребінкою імпульсів заданого періоду.
3. Максимум кореляції = зсув фази. Одна цифра, миттєво.
4. Далі фазу тримає той самий particle filter із **зафіксованим періодом** — компенсує
   лише дрейф виконавця.

> **Як це вийшло насправді (Фаза 6).** Пункти 1–3 згорнулися в одну величину.
> Кроскореляція з гребінкою при відомому періоді — це перший коефіцієнт Фур'є на
> цьому періоді, тобто два акумулятори із загасанням замість буфера на 2–3 с і
> перебору зсувів. Окремий поріг на «музика почалась» виявився зайвим: у шумі
> онсети є, а фази немає, тож міра концентрації відповідає на обидва питання
> одразу. Натомість довелося додати те, чого в плані не було, — критерій, за яким
> концентрацію можна вважати невипадковою (статистика Релея), інакше режим
> «синхронізується» з будь-чим. Деталі — у Фазі 6 дорожньої карти.

## 6. Офлайн-аналіз файлів

### Конвеєр

```
файл → декодування → моно 48 кГц → ODF → глобальний темп
     → DP-трекінг долей → двонаправлений downbeat + розмір
     → сітка долей → кеш на диску (JSON/бінарно, ключ = хеш файлу)
```

Розбір робиться **один раз** і кешується. Трихвилинний трек на сучасному телефоні —
одиниці секунд; у UI це прогрес-бар при імпорті, далі миттєво.

### Декодування

| Формат | Як | Де |
|---|---|---|
| mp3, wav, flac, ogg | `dr_libs` / `stb_vorbis` | у ядрі, портативно |
| m4a, aac | AVAssetReader / MediaCodec | платформенно |

### ⚠️ Обмеження, яке треба знати заздалегідь

**Треки з Apple Music, Spotify та інших стримінгів прочитати неможливо.** Вони захищені
DRM, і жоден API не дасть до них доступ як до сирого аудіо. Це не обхідна проблема —
це навмисне обмеження платформ.

Працюють: власні файли користувача (Files / Downloads), незахищені покупки, експортовані
мінусовки, записи з диктофона. У UI це треба пояснити м'яко й одразу, бо інакше перше,
що зробить користувач — спробує додати трек із Apple Music і вирішить, що застосунок
зламаний.

Часткова компенсація: якщо стримінг грає з іншого застосунку **вголос**, працює
мікрофонний режим Auto. Гірше за файл, але не глухий кут.

### Що це відкриває

Коли трек розібрано і програється з застосунку, ми знаємо позицію відтворення **точно**.
Це прибирає з основного сценарію всю невизначеність детекції — і додатково дає:
- перемотування по тактах, а не по секундах;
- зациклення складного місця рівно по межах такту;
- відлік «раз-два-три-чотири» перед вступом;
- зміну темпу треку без зміни висоти (time-stretch) для повільного розучування;
- у Фазі «зворотний зв'язок» — порівняння голосу з еталонною сіткою, а не з оцінкою.

## 7. Точність часу

Найчастіша причина, чому саморобні метрономи «плавають».

**Ніколи не грати клік по команді.** `play()` у момент долі дає джитер 20–50 мс.
Кліки **плануються наперед** у майбутньому часі:

```swift
let when = AVAudioTime(hostTime: beatHostTime - outputLatencyInHostTicks)
player.scheduleBuffer(clickBuffer, at: when, options: [])
```

Планувальник тримає чергу на 2–3 долі вперед і переписує її, якщо трекер змінив оцінку.

**Один годинник на все.** Уся система в одному часовому домені (`mach_absolute_time`
на iOS, `CLOCK_MONOTONIC` на Android). Час приходу семпла беремо з таймстемпа
аудіо-колбека, а не з системного годинника.

**Компенсація затримок:**

| Канал | iOS | Android |
|---|---|---|
| вхід | 5–30 мс | 10–100 мс, дуже різниться |
| вихід | 10–40 мс (BT: до 200) | 20–150 мс, дуже різниться |
| вібрація | ~10–20 мс | 20–50 мс, різниться |
| екран | 1 кадр (8–16 мс) | 1 кадр |

**Android — окрема історія.** Затримка там гірша й значно менш передбачувана, ніж на iOS.
Oboe дає найкраще з можливого, `AudioManager.getOutputLatency` бреше на багатьох
пристроях. Тому **екран калібрування на Android обов'язковий**, а не опційний:
користувач стукає в такт із кліком, ми вимірюємо його систематичний зсув і компенсуємо.
На iOS той самий екран лишається опційним — для Bluetooth-навушників.

**Цільові показники (iOS):**
- джитер кліку < 2 мс,
- похибка позиції долі відносно еталону < 20 мс,
- затримка «зміна темпу → підлаштування» < 2 с.

Для Android цілі встановлюємо після замірів на реальних пристроях — обіцяти ті самі
цифри наперед було б нечесно.

## 8. Проблема зворотного зв'язку

Оскільки звук у динамік увімкнено (за бажанням користувача), мікрофон чує власний клік.
Без запобіжника трекер захоплюється власним сигналом і «підтверджує» будь-який
неправильний темп, у який один раз влучив.

**Рішення — часове стробування, а не повна ехо-компенсація.** Ми точно знаємо, коли
пролунає клік (самі його запланували), і він короткий (~30 мс). Тож просто **не оновлюємо
ODF у вікні ±40 мс навколо кожного власного кліку**. На 120 BPM це ~15% викинутих
кадрів — трекер це переживає без проблем.

Це краще за вбудовану ехо-компенсацію (`setVoiceProcessingEnabled` / `AcousticEchoCanceler`):
вона розрахована на мову, застосовує агресивну фільтрацію й AGC і псує сигнал саме
в потрібному нам діапазоні.

Те саме стробування працює й для звуку мінусовки, якщо вона грає з динаміка, — але
там ми знаємо весь сигнал наперед, тож за потреби можна зробити й повноцінне віднімання.

Вібрація й візуал від цієї проблеми вільні взагалі — для співака на репетиції це,
ймовірно, взагалі кращий основний канал.

## 9. ML-моделі

### Що ставимо в застосунок

**BeatNet** (`mjhydri/BeatNet`, ISMIR 2021): «CRNN and Particle Filtering for Online
Joint Beat, Downbeat and Meter Tracking» — буквально формулювання нашої задачі: онлайн,
спільно біти + сильна доля + розмір. Ліцензія **CC BY 4.0**, комерційне використання
дозволене. Ваги — **1.54 МБ**. Архітектура: Conv1d → pool → Linear → однонапрямлений
LSTM → softmax; 22.05 кГц, крок 20 мс. Операції стандартні, блокувальників для ONNX не
виявлено — але каскадний particle filter живе в NumPy поза графом і його доведеться
портувати в C++ руками.

Шлях у застосунок: PyTorch → **ONNX** → ONNX Runtime Mobile.
Один артефакт моделі на обидві платформи; апаратне прискорення через execution providers
(CoreML на iOS, NNAPI/XNNPACK на Android). Якщо профілювання покаже, що на iOS
конвертація в `.mlpackage` дає відчутний виграш — можна возити два артефакти з одного
ONNX, але починаємо з одного.

### Beat This! — для офлайн-режиму

**MIT, включно з вагами** — рідкість серед офлайнових моделей і головна причина
вибору. Варіант `small` — 8.1 МБ. Існує готовий C++-порт із конвертованою ONNX-моделлю.
Не причинна (дивиться вперед і назад), тож лише для файлового режиму — але саме там
вона й потрібна, і саме там точність найвища. Розміру такту не видає.

### Що використовуємо лише в дослідженні

**madmom** — багаторічний еталон точності, джерело псевдо-розмітки і стеля для
порівняння. Практично: PyPI заморожений на 0.16.1 (2018), Python ≤3.7, ламається на
сучасному NumPy — у нашому Python 3.11 не запуститься без окремого оточення.

**All-In-One** (`mir-aidj/all-in-one`, MIT) — залежить від NATTEN, кастомної операції
уваги, що **блокує експорт в ONNX**. Плюс Demucs і GPU. Тільки як референс.

### ⚠️ Виправлення до попередньої редакції цього плану

Тут була помилка, і в бік, протилежний до обережного. Я писав, що ліцензія madmom
«BSD-подібна із застереженням щодо комерційного використання, у продукт не тягнемо».
Насправді madmom **подвійно ліцензований**: код під BSD-2, а **файли моделей і даних —
під CC BY-NC-SA 4.0**. Тобто алгоритмічний код комерційно придатний, заборонені саме
передтреновані ваги. Практичного рішення це не змінює (у продукт усе одно йде BeatNet),
але сама підстава була сформульована невірно.

Так само `taejunkim/allinone` на HuggingFace **підтвердити не вдалося** — канонічне
джерело на GitHub.

### Повна перевірка — в окремому документі

[`docs/ml-models.md`](ml-models.md) містить перевірені ліцензії, розміри, ідентифікатори
репозиторіїв і аналіз наборів даних, із явним поділом на «перевірено на власні очі» і
«не вдалося підтвердити». Там же — важливе обмеження: `huggingface.co`, `zenodo.org`
і `arxiv.org` віддавали 403, тож **живу доступність посилань на завантаження наборів
даних не перевірено**. Ліцензії й код репозиторіїв перевірені по-справжньому, через GitHub.

## 10. Оцінка якості

Без вимірювання цю задачу зробити неможливо — «на слух здається, що працює» розвалюється
на першому ж вальсі.

**Метрики** (стандарт MIREX, `mir_eval.beat`):
- **F-measure** з допуском ±70 мс — основна;
- **CMLt / AMLt** — неперервність трекінгу, причому AMLt пробачає помилку в октаві темпу,
  що показує, які саме помилки ми робимо;
- окремо **downbeat F-measure** — він завжди помітно гірший за beat F-measure.

Метрики рахуються **окремо для офлайн- і онлайн-трекера**. Офлайн має бути відчутно
кращим; якщо ні — щось зламано.

**Дані:**
- публічні набори з розміткою: Ballroom, Hainsworth, SMC, GTZAN-Rhythm (частина потребує
  запиту на доступ — закласти час);
- **власний набір** — критично: 30–50 записів саме у ваших умовах. Спів під мінусовку
  з телефона, гітара в кімнаті, репетиція гурту, шумне приміщення. Публічні набори
  складаються зі студійних записів і систематично завищують очікування.

**Тест на регресію часу** — окремо від якості алгоритму: прогін метронома на пристрої
з записом власного виходу через аудіо-інтерфейс і вимірюванням реального джитера.
Ловить помилки планування, яких не видно в Python. На Android — на кількох різних
пристроях, бо розкид великий.

ODF, оцінка темпу, офлайн-трекер на динамічному програмуванні, синтетичні дані,

### Фаза 1' — Настільний стенд на Windows ✅ (лишився живий мікрофон)

запис свого ж виходу.
*Зроблено: `tiktak devices | play | render | measure`; збірка під Windows і Linux у CI.*

**Сам метроном опинився в ядрі, а не у стенді.** `render::ClickRenderer` синтезує
клік, `render::Metronome` — це аудіоколбек цілком. Оболонки відрізняються тим, як
дістають буфер і годинник, і **не мають** відрізнятися тим, що відбувається між ними;
розписаний у кожній оболонці окремо, цей код став би трьома копіями, що розходяться, а
розходження виглядало б як метроном, який добре міряється на стенді й погано звучить
на телефоні.

**Режим `render` — не другорядний.** Він проганяє той самий колбек проти віртуального
годинника й пише WAV. Це те, що робить таймінг метронома перевірюваним **без залізяччя**:
CI на кожен пуш рендерить 20 секунд на 137 BPM і перевіряє, що кожна доля лягла на свою
вибірку. 137 навмисно: темп, який не ділить частоту
дискретизації, — саме той випадок, який ловить помилку заокруглення.

Один справжній баг звідти і виліз: клік, чия найближча вибірка припадала вже на
наступний буфер, затискався в поточний — помилка в цілу вибірку, непомітна на 120 BPM.

`measure` грає метроном і одночасно пише вхід, далі шукає кожен клік у записі. Дає два
числа: **середнє** — це затримка, її можна скомпенсувати (`--latency-ms`); **розкид** —
це джитер, його скомпенсувати не можна, і саме він чується як метроном, що не стоїть на
місці. Потребує петлі вихід→вхід (кабель або колонки з мікрофоном).

Живий мікрофонний вхід додано у Фазі 5 разом із онлайн-трекером — окремо від нього
перевіряти було нічого.

### Фаза 3 — Офлайн-аналіз файлів у C++ ✅
Порт оцінки темпу й офлайн-трекера з Python у `core/analysis/`, потоковий фасад
`OfflineAnalyzer` (аудіо блоками → сітка долей), C API `tt_offline_*`.
Декодування WAV/FLAC/MP3 через dr_libs — **окрема бібліотека** `tiktak_decode`,
щоб `tiktak_core` лишився без сторонніх залежностей (див. нижче).
*Зроблено: 198 тестів, чисто під `-Werror` і ASan/UBSan; паритет C++↔Python —
**часи всіх долей збігаються біт у біт**, впевненість до 1e-8; наскрізний тест
бере справжній mp3 і видає сітку долей.*

**Декодування приймає байти, а не шлях.** Це не дрібниця: на Android вибраний файл
приходить як `content://`-дескриптор, на iOS — як security-scoped URL, а на Windows
шлях із кирилицею не переживає вузькосимвольний `fopen`, який неявно припускає
path-орієнтований API. Байти вміє віддати будь-яка оболонка — робочий шлях уміє не
кожна. Варіант зі шляхом лишено як зручність для стенда й тестів.

**Формат визначається за вмістом, і невідоме відхиляється.** MP3-декодер, якому дати
довільні байти, видасть не помилку, а шум — і мовчки аналізувати шум гірше, ніж
сказати «формат не підтримується». Одинадцяти одиничних бітів синхрослова замало:
перевіряються ще поля шару й бітрейту.

**Кеш сітки долей — байти, а не файли.** Ядро серіалізує готовий аналіз у блоб
і відновлює з нього (`tt_offline_grid_serialize` / `tt_offline_grid_restore`);
де його зберігати — вирішує оболонка, з тієї ж причини, з якої декодування
приймає байти: байти вміє покласти на диск будь-яка платформа, а портативного
поняття «тека кешу» не існує. Ключ — SHA-256 від байтів *закодованого* файлу
(`tt_grid_key`): перейменований файл влучає в кеш, перекодований — коректно
промахується, і нічого не треба декодувати, щоб це з'ясувати. Конфігурація —
частина ідентичності сітки: той самий трек із ручним `bpm_hint` — інша сітка,
і віддати замість неї автоматичну означало б долі не там, де треба. Обрізаний
чи побитий блоб читається як промах (контрольна сума), а не як коротша сітка.

### Фаза 4 — Відтворення з метрономом ✅ (на стенді)
Програвання треку синхронно з сіткою, відлік перед вступом, зациклення по тактах.
*Зроблено: `render::TrackPlayer` у ядрі, C API `tt_player_*`, команда
`tiktak track` у стенді; 200 тестів, чисто під ASan/UBSan; CI ганяє повний
шлях mp3 → аналіз → кеш → рендер із кліком двічі й звіряє байт у байт.*

**Клік не компенсується відносно треку — вони виходять одним буфером.** Клік
пишеться на той самий семпл потоку, де грає його доля, і приходить до вуха
разом із нею за будь-якої затримки виводу. Затримкова арифметика лишається
тільки в haptic/visual-підказках, які компенсуються відносно моменту, коли
доля *чутна* (час семпла + вихідна затримка).

**Програвач — окремий клас, а не режим метронома.** Джерело часу обернене:
метроном породжує сітку з темпу, програвач іде за сіткою, яку вже зафіксував
аналіз — авторитет щодо того, де доля, у треку, а не в годиннику. Відлік
перед вступом рахує з локального інтервалу сітки в точці входу (на rubato
глобальний BPM бреше), зациклення стрибає семпл-у-семпл з першої долі
кінцевого такту на першу долю початкового.

**Такти більше не бухгалтерія.** `downbeat_offset` і `beats_per_bar` тепер
приходять з аналізу (Фаза 7), а не з конвенції; користувач і далі може їх
зсунути, і `--beats` перекриває знайдене.

Лишається оболонка (Фаза 8): на телефоні той самий `tt_player_*` отримує
буфер і годинник від AVAudioEngine/Oboe.

### Фаза 5 — Реалтайм із мікрофона ✅ (на стенді)
Онлайн-трекер (particle filter) у C++, стробування власного кліку.
*Зроблено: `tracking::BeatParticleFilter` і `tracking::LiveTracker` у ядрі,
`render::LiveMetronome` (трекер + клік + арифметика затримок), C API `tt_live_*`,
команда `tiktak listen` у стенді — з мікрофона або з файлу; 254 тести, чисто під
ASan/UBSan; CI ганяє мікрофонний шлях на справжньому mp3 без жодного мікрофона.*

**Трекер передбачає, а не детектує.** Клік треба записати в буфер до того, як доля
прозвучить, тож питання не «де були долі», а «де наступна». Динамічне програмування
офлайн-трекера тут не працює за визначенням — воно потребує всього сигналу наперед.

**Спостереження з нульовим середнім.** Онсет зсуває вагу частинки на
`онсет · (вікно(відстань до її долі) − середнє вікно)`, тож кадр без онсету не зсуває
нічого. Тиша коштує лише дифузії — хмара котиться за останнім темпом замість
вчепитися в перший-ліпший шум, — і саме це робить **безпечним викидання кадрів**, на
яке спирається стробування власного кліку.

**За кожну передбачену долю частинка платить.** Без цього доданка ніщо не заважає
подвійному темпу: частинка, що б'є вдвічі частіше, влучає в кожен справжній онсет, а
за долі, поставлені в проміжки, не платить нічого — бо кадр без онсету ваги не рухає.
Це інтегральний доданок правдоподібності точкового процесу, масштабований тим, скільки
онсет-енергії зараз коштує доля, — тому тиша лишається безкоштовною.

**Доказ — квадрат онсету, в одиницях «доля = 1».** Майже в усій музиці є удари між
долями, і при вазі, пропорційній амплітуді, хай-хет утричі тихіший купує третину
віри долі. Тоді доля та її власний підподіл опиняються в межах шуму одна від одної, і
трекер миготить між ними — це рівно те, що ми побачили на тестовому mp3 з вісімками.
Квадрат робить той хай-хет вартим дев'ятої частини. Нормування — за поточним **піком**,
а не за z-оцінкою: z-оцінка їде разом із матеріалом, і щільна музика давала б слабший
доказ просто тому, що її більше.

**Впевненість = згода × збіг.** Ресемплінг змушує хмару погодитися сама з собою за
кілька секунд навіть на білому шумі, тож фільтр, який звітує лише про власну
концентрацію, звітує майже-певність там, де долі немає взагалі. Друга половина —
частка онсет-енергії, що й далі лягає на передбачення. Обидві мають виконуватись.

**Стробування власного кліку.** Метроном, який слухає через мікрофон, чує сам себе, а
клік — найонсетніший звук на світі. Без стробування трекер чіпляється за власний вихід:
впевненість іде в одиницю, темп перестає реагувати на кімнату, і ніщо у виході не
виглядає зламаним. Відняти клік не можна — відгук кімнати на нього невідомий, — тож
трекер просто не дивиться у вікно, яке той займає. Це коштує інформації, але **не
зміщує** фільтр, бо спостереження нульове в середньому: викинутий кадр не рухає ваг
узагалі, тоді як однокандидатний трекер від «проігнорованого» кадру все одно поїхав би.

**Уся арифметика затримок — це одне число, і воно скорочується.** Годинник трекера —
годинник запису: подія в кімнаті о фізичному `T` потрапляє туди о `T + затримка входу`.
Щоб клік **почули** на долі `b`, його треба віддати за `b − повний оберт`. А почує його
мікрофон рівно о `b` — оберт повертається дорогою назад, — тож вікно, яке стробується,
це саме передбачена доля, без жодної поправки.

**Відома й прийнята межа:** на матеріалі помітно поза 100–140 BPM трекер інколи сідає
на сусідню октаву — повільну п'єсу веде по вісімках, швидку в half-time. Це робота
темпового пріора, це найчастіша помилка всіх бітових трекерів, і саме для неї в UI
кнопки ×2 / ÷2.

### Фаза 6 — Manual + sync ✅ (на стенді)
Вирівнювання фази при заданому вручну BPM.
*Зроблено: `tracking::PhaseSync` у ядрі, фіксація періоду в particle filter
(`pinPeriod` / `seedPhase`), C API `tt_live_set_manual_tempo` / `tt_live_waiting`,
`tiktak listen --manual N` у стенді; 285 тестів, чисто під ASan/UBSan; CI
перевіряє на справжньому mp3 обидві половини — що режим синхронізується на
120 і що **відмовляється** на 137.*

**Кореляція з гребінкою при відомому періоді — це одне комплексне число.**
Питання «де доля» при заданому періоді — це питання, як розподілена онсет-енергія
*за модулем періоду*, а перший коефіцієнт Фур'є на цьому періоді і є центром маси
цього розподілу на колі. Тобто ані буфера на 2–3 с, ані перебору зсувів: два
акумулятори із загасанням, і фаза виходить з `atan2` без квантування до кадру
ODF. Використання лише основної гармоніки робить гребінку косинусною замість
імпульсної — і це навмисно: різку гребінку доводиться десь дискретизувати, і на
частоті кадрів вона починає віддавати перевагу одним зсувам перед іншими.

**Сама по собі концентрація нічого не означає.** Онсети з випадковими фазами
однаково дають результуючу приблизно один-на-корінь-із-їх-кількості, тож
«переконливо» залежить від того, скільки їх було: шість онсетів із концентрацією
0.4 — це рівно те, що робить випадковість. Критерієм узяв статистику Релея
(квадрат результуючої на ефективну кількість онсетів), і саме вона дозволяє
режиму **відмовитись**. Кімната на 150, коли на шкалі 120, не має фази 120 —
її онсети рівномірно обходять коло, — і сказати про це чесніше, ніж клікати
абиде й називати це синхронізацією. Синхронізатор, який синхронізується завжди,
не сказав нічого.

**Доказ — куб онсету, різкіше ніж у фільтра.** У фільтрі удар між долями лише
знижує частинки, які його не передбачили; тут удар рівно посередині стоїть під
протилежним кутом і **віднімається** від відповіді. Хай-хет на 0.7 від долі
лишає результуючу 0.18 при вазі за амплітудою і 0.34 при вазі за енергією — в
обох випадках відповідь правильна, але виглядає надто слабкою, щоб на неї
спиратися. У кубі це 0.49. Виміряно на дванадцяти сценаріях (чисті долі,
підподіли всіх сил, шум, тиша, кімнати з чужим темпом): квадрат приймає шість
із семи, які має прийняти, куб — усі сім, і жоден із них не ведеться на п'ять,
які має відкинути.

**Кореляція знаходить, фільтр тримає.** Кореляція — це середнє, тож синкопований
такт її тягне; вікно фільтра локальне, тож випадковий удар лише знижує частинки,
що його не вгадали. Фазу передаємо один раз, далі її несе хмара із зафіксованим
періодом, і кімнаті дозволено зсувати клік не більш ніж на 2% долі за раз — досить
швидко для виконавця, що пливе, і надто повільно, щоб гнатися за темпом, якого
ніхто не просив.

**Дві властивості режиму випали з фільтра, а не були дописані.** При
зафіксованому періоді темповий пріор і плата за долю більше не розрізняють
жодних двох гіпотез — обидва вимикаються. А оскільки спостереження нульове в
середньому, кімната, що замовкла, не рухає ваг узагалі, і сітка просто триває
далі — тобто метроном, який тримає темп користувача крізь тиху репризу, вийшов
безкоштовно.

**Детекція «початку мелодії» окремим порогом не потрібна.** У шумі кімнати
онсети є, а фази немає — та сама міра концентрації, яка відповідає «де доля»,
уже відповідає «чи вона взагалі є». Питати двічі означало б завести ще один
рівневий поріг, який можна виставити неправильно.

### Фаза 7 — Сильна доля і розмір ⚙️ (портативна половина — на стенді)
Ознаки по долях, рішення про такт і весь шлях від аудіо до акценту на першій
долі — без сторонніх залежностей. ONNX Runtime, Beat This! і BeatNet
лишаються попереду.

**Динамічного програмування немає, і це результат, а не спрощення.** План
вимагав марковського згладжування поверх ймовірності `P(downbeat|beat)`, щоб
одна гучна доля не зсувала межу такту. Але згладжування потрібне лише тому,
що модель під ним відповідає *подолево*, а розмір, який не змінюється, має
рівно один додатковий ступінь свободи — фазу. Зафіксуй розмір і фазу, і всі
межі такту в п'єсі визначені. Тобто весь простір гіпотез — десяток пар
(розмір, фаза), кожну з яких можна оцінити точно, і згладжування, яке прохід
Вітербі лише наближає, тут уже повне. Ціна названа в заголовку: п'єса, що
**змінює** розмір посеред себе, не представима — саме для цього DP довелося б
повернути, і саме для цього, а не заради згладжування.

**Оцінка — контраст, а не сума.** Сума по вибраних долях автоматично віддає
перемогу найкоротшому такту: 2/4 забирає половину долей там, де 4/4 забирає
чверть. Різниця середніх — ні.

**Повносмуговий акцент вимкнено за замовчуванням, і це вимірювання.** «Наскільки
сильно вдарено долю» звучить як ознака сильної долі й насправді майже
протилежна їй: у звичайному рисунку «бочка на раз, малий на бекбіт» малий
широкосмуговий, а бочка — ні, тож повносмугова ODF має пік на 2 і 4, а нижня
смуга — на 1. На еталонному кліпі акцент дає в середньому 1.2 на бекбітах
проти 0.68 на сильній долі, нижня смуга — 1.13 проти 0.73. З вагою 0.5 акцент
перемагав, і аналіз упевнено акцентував четверту долю. Ознака справжня там, де
сильна доля дійсно найгучніша подія (оркестр, хор), тож вона лишилася
параметром — просто не безпечним типовим значенням.

**Хрому не стандартизують, на відміну від онсетних ознак.** Косинусна відстань
між профілями висот уже має абсолютний сенс, а величина онсету не має жодного,
доки її не порівняли з рештою п'єси. Стандартизація хроми взяла б шум рівня
0.01 на суто ударному треку й підвищила б його до рівноправного голосу з
бочкою.

**Чого хрома не бачить.** Нижню межу діапазону піднято до тієї частоти, де
півтон ще ширший за пару бінів FFT: при 48 кГц і вікні 2048 це близько 800 Гц.
Тобто гармонію видно за верхніми обертонами акорду, а не за його основними
тонами. Виміряно, що цього досить — `TheHarmonyAloneFindsTheBarWithNoDrumsToHelp`
знаходить межу такту з вимкненими ритмічними ознаками. Довше окреме вікно або
constant-Q — справжнє рішення, і його тут немає.

**Нормалізація профілю — та сама пастка, що й вибілювання в ODF.** Ділення на
довжину, що прямує до нуля, підіймає спектральний витік до повної шкали, і
басова нота під межею роздільності повертається як упевнений акорд, зібраний з
нічого. Поріг заданий відносно всього спектра, тож тримається за будь-якого
підсилення на вході.

**Чому ONNX ще немає.** Модель — це друга половина фази, і портативна половина
мусить існувати незалежно від того, що саме рахує `P(downbeat|beat)`: ознаки,
рішення, кеш, C API, акцент у кліку. Тепер у моделі є вимірюваний базовий
рівень, який треба перевершити, а не порожнє місце, яке треба заповнити.

**Двох речей ця половина ще не має, і фаза не закрита саме через них.**
По-перше, увесь матеріал перевірки — синтетичні кліпи з відомою істиною та
один згенерований MP3; це доводить, що частини зібрані правильно, і нічого не
каже про реальну музику. По-друге, поріг `margin = 0.25`, за яким акцент
вимикається, вибрано з кількох спостережень, а не відкалібровано: його треба
підібрати на validation-наборі й один раз перевірити на відкладеному. Обидва
пункти впираються в те саме — розмічений набір записів, якого ще немає, і саме
його треба зробити перед інтеграцією будь-якої моделі, інакше дві моделі буде
нічим порівняти.

**Апарат для цього вже стоїть** — `research/eval/` (див. `research/eval/README.md`).
`tools/eval/dump_analysis` виводить аналіз у JSON, тож оцінюється саме той core,
що збирається в застосунок, а не пітонівське переписування. Метрики рахують
розмір окремо від фази — downbeat F-measure не бачить помилки розміру, бо 4/4,
назване 2/4, влучає в кожну справжню межу такту й дає ≈ 0.67, що виглядає
пристойно для неправильної відповіді. Поріг `margin` обирається розгорткою:
найнижчий, що вкладається в бюджет помилкових акцентів, бо утримання коштує
функції, а помилковий акцент — дубля. Вибір на validation, одна перевірка на
відкладеному.

Бракує тільки записів: у цьому середовищі аудіо взяти нізвідки — проксі блокує
huggingface і zenodo. На синтетиці апарат перевірений і вже показує, чого варта
калібровка на 13 кліпах: поріг з нульовою частотою помилок на validation дає 14%
на held-out. Синтетика ж не вправляє гармонічну підказку взагалі — у неї немає
зміни акордів, — тож вона лишається регресійним сигналом (`--expect-correct 10`
у CI), а не калібровкою.

*Зроблено: `dsp::ChromaFilterbank` і `analysis::beatFeatures`/`findDownbeats` у
ядрі, C API `tt_offline_beats_per_bar` / `tt_offline_downbeats` / міри довіри,
формат кешу v2, акцент першої долі в `tiktak track`; 324 тести, чисто під
`-Werror` і ASan/UBSan.*

### Фаза 8 — iOS-оболонка
SwiftUI + AVAudioEngine + CoreHaptics поверх готового й перевіреного ядра.
Навмисно пізно: до цього моменту вся логіка вже відлагоджена на стенді, тож на
повільний TestFlight-цикл лишається мінімум — прив'язка до пристрою, гаптика,
абсолютні затримки, UI.
*Потрібно: для розробки й запуску на власному пристрої достатньо безкоштовного
Apple ID у Xcode (профіль живе 7 днів і поновлюється перезбіркою). Платні $99/рік
потрібні для TestFlight і публікації — тобто ближче до кінця фази, а не на її
початку.*

Порівняння онсетів голосу з сіткою долей, статистика по сесії.

Compose + Oboe; App Store і Google Play.

## 14. Розподіл праці

**Що робиться в цьому контейнері (Linux):**
- уся папка `research/` — прототип на Python, harness, експерименти, звіти з метриками;
- **`core/` — повністю**: C++ пишеться, збирається і тестується тут нативно (googletest,
  CMake). Це велика частина проєкту, і вона перевіряється по-справжньому, а не наосліп;
- скрипти конвертації моделей, `docs/`, ADR;
- **написання** Swift/Kotlin-коду.

**Що робиться на вашій Windows-машині:**
- **настільний стенд** — реальний мікрофон, реальний вивід, вимірюваний джитер,
  інтерактивна ітерація в секундах. Основне місце розробки й налагодження;
- запуск усіх тестів ядра і дослідницької частини.

**Що можливе лише через CI + TestFlight:**
- збірка iOS, встановлення на iPhone, перевірка гаптики й абсолютних затримок iOS;
- цикл 15–45 хвилин, без точок зупину й без Instruments.
  Тому кожен вихід на пристрій має бути прицільним, з наперед складеним списком того,
  що саме міряємо.

**Що потребує Mac (якщо з'явиться):** інтерактивне налагодження, Instruments, швидкий
цикл на пристрої, реліз у App Store без CI-обхідних шляхів.

Винесення ядра в C++ дало побічний плюс: **більшу частину логіки тепер можна повноцінно
розробляти й тестувати тут**. Раніше весь DSP на vDSP був би непротестованим до вашої
збірки. Тепер непротестованими лишаються лише тонкі платформенні оболонки.

## Відкриті питання

1. **UI: SwiftUI + Compose нативно, чи спільний Flutter?** Моя рекомендація — нативно
   (поверхня UI мала, а кадрово точна анімація долі важлива). Рішення потрібне на початок
   Фази 1.
2. **Комерційний застосунок чи для себе?** Впливає на вибір ліцензій моделей і на те,
   чи закладати монетизацію в архітектуру одразу.
3. **Наскільки ви впевнено почуваєтесь у C++, DSP і ML?** Від цього залежить, наскільки
   детально коментувати код і чи писати пояснювальні документи до кожного алгоритму.
4. **Android — одразу після iOS чи «колись»?** Ядро й CI готуємо однаково в обох випадках,
   але від відповіді залежить, наскільки рано інвестувати в JNI-шар і тестові пристрої.
