# ADR 0003 — Розробка на Windows без Mac: настільний стенд як основне робоче середовище

**Статус:** прийнято
**Дата:** 2026-07-25
**Замінює частину:** ADR 0002 лишається чинним, але порядок платформ у PLAN.md змінено

## Контекст

Робоча машина — **Windows**, цільовий пристрій — **iPhone**, iOS обов'язковий.

Xcode працює лише на macOS, і жоден крос-платформний фреймворк цього не змінює:
Flutter, React Native та будь-що інше однаково викликає Xcode на етапі створення
iOS-бінарника. Це обмеження тулчейну Apple.

Отже, з наявним залізом:

| Що потрібно | Чи доступно |
|---|---|
| Зібрати iOS-бінарник | лише через macOS у CI або хмарі |
| Поставити на iPhone | лише TestFlight; Apple Developer Program $99/рік |
| Точки зупину, Instruments | **недоступно** |
| Заміряти реальну затримку на iPhone | лише через TestFlight-цикл, 15–45 хв на ітерацію |

Симулятор iOS не рятує навіть за наявності хмарного Mac: він не відтворює ні
CoreHaptics, ні реальну затримку аудіотракту — тобто саме ті дві речі, навколо яких
побудований застосунок.

## Проблема

Метроном — це застосунок про мілісекунди. Основна робота Фази 1 полягає у вимірюванні
й усуненні джитера, а це вимагає **швидкого циклу на реальному залізі**. Цикл у 30 хвилин
робить таку роботу практично неможливою: за день виходить десяток спроб замість сотні.

## Рішення

**Перенести максимум роботи в те, що вимірюється на Windows, і зробити iOS-оболонку
настільки тонкою, наскільки це взагалі можливо.**

Конкретно — додати `desktop/`: настільний стенд на Windows поверх того самого
`core/`, з реальним аудіо через **miniaudio** (single-header, public domain, WASAPI
на Windows). Він дає те, чого не дає ні CI, ні хмарний Mac:

- реальний мікрофон у реальній кімнаті;
- реальний вивід і **вимірюваний** джитер кліку — через петлю запису власного виходу;
- інтерактивну ітерацію в секундах;
- перевірку планувальника долей, стробування власного кліку та онлайн-трекера
  на живому звуці.

Це не «прототип, який потім викинемо». Планувальник долей, компенсація затримок,
стробування і трекер — усе це портативний C++ у `core/`. Стенд лише під'єднує до
нього реальні пристрої. На iOS та сама логіка отримує AVAudioEngine замість
miniaudio, і це буквально інший файл захоплення/відтворення.

### Наслідок для розподілу коду

Правило посилюється: **якщо щось можна покласти в `core/`, воно кладеться в `core/`.**
Раніше це був аргумент про Android; тепер це умова того, що проєкт узагалі можна
налагоджувати. У платформенній оболонці лишається тільки те, що фізично не може бути
портативним: доступ до аудіопристроїв, гаптика, вибір файлу, UI.

### CI від першого дня

GitHub Actions збирає iOS-таргет на кожен пуш. Не для тестування — для того, щоб
iOS-збірка ніколи не «протухла» непомітно, бо виявити це на TestFlight-циклі
коштувало б днів.

## Наслідки

**Добре:**
- Основна робота стає можливою на наявному залізі.
- Стенд корисний назавжди: він лишається місцем, де відлагоджують алгоритми, і після
  появи Mac.
- Windows-версія — потенційно окремий продукт для музикантів за комп'ютером.

**Погано:**
- Нова платформа в проєкті (+кілька тижнів на стенд).
- Затримка й поведінка WASAPI **не** відповідають iOS. Стенд валідує логіку й алгоритми,
  але **не** абсолютні числа затримки на iPhone — їх однаково доведеться міряти на
  пристрої, просто рідше й прицільніше.
- Гаптику на Windows не перевірити взагалі.

**Обов'язкові витрати, якщо iOS лишається метою:**
- Apple Developer Program — $99/рік, без варіантів.
- Або доступ до Mac (вживаний Mac mini ~$350–450), або життя з циклом CI+TestFlight.

## Що це не змінює

`core/`, C API, дослідницька частина на Python і ADR 0001 лишаються без змін —
рішення винести ядро в портативний C++ виявилось значно ціннішим, ніж передбачалось
при його ухваленні.

ADR 0002 (нативний UI) теж лишається чинним: крос-платформний фреймворк не усунув би
потребу в macOS, тож єдиний аргумент на його користь тут не працює.
